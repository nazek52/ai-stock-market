# Передача этапа 6, участник B

## Интеграция в общую ветку

Root подключил marketNewsProvider к Inngest и ручному preview: новости принадлежат символам из сохранённого watchlist; для пустого списка используется общий рынок. Синтетические новости используют переданный clock, поэтому не отбрасываются как будущие при проверке 24 часов. Ручной preview ограничен 3 запросами за 5 минут на собственную сессию.

Better Auth подключён к verification/reset письмам; токены действуют час, сброс отзывает прежние сессии. В production подтверждение адреса обязательно. В локальном режиме автоотправка при регистрации включается только с EMAIL_ENABLED=true и SMTP. afterEmailVerification сохраняет welcome intent, не вызывает сеть Inngest. Reconciler подбирает подтверждённые аккаунты, для которых запись intent не удалась. Проверки Origin/CSRF явно включены и в тестовой среде.

Общие проверки после интеграции: npm run check — lint, типы, 90 unit-тестов и production build прошли; digest integration — 15 тестов, digest-market — 2, auth-email — 6, прежние auth-profile — 8 прошли на реальных временных MongoDB replica set. Production audit — 0 известных уязвимостей. Внешняя отправка и cloud-расписания пока не проверены.

Ограничение масштабирования: общий Finnhub бюджет 30/мин разделяется с UI и алертами. Холодная загрузка новостей по длинному watchlist может исчерпать его; функция завершится типизированной ошибкой и повтором, не подставит выдуманные новости. До live-рассылки необходим нагрузочный прогон выбранной аудитории и квоты, настройка durable загрузки по символам либо утверждённого тарифа. Локальные фикстуры не подтверждают ёмкость live-поставщика.

Задачи P6.1, P6.2, P6.3, P6.5: серверная реализация выполнена и проверена локально в отдельном worktree от `38ee950`. Production-приёмка не выполнена: внешних аккаунтов/лицензий, реальных ключей, домена отправителя и согласованного шаблона A пока нет. ## Контракты для интеграции

- `sendTransactionalEmail({ idempotencyKey, type, userId, payload, previewOnly? }, transport?)` — единый серверный путь доставки. `type`: `digest`, `welcome`, `price_alert`, `verify_email`, `reset_password`. Стабильный idempotency key формируется из сохранённого события, а не из номера попытки. Payload принимает только subject/title/paragraphs/links/fixture; произвольного HTML нет. Возвращает `status`, безопасную `reason` и, только для preview, отрендеренный результат.
- `processDigest(userId, localDate, { newsProvider, summaryGenerator?, transport?, now?, previewOnly? })` — изолированный выпуск. `NewsProvider(symbols, now)` возвращает `{source:'fixture'|'finnhub', articles:StockNewsItem[]}`. Читает `watchlist_items{userId,symbol}` до 100 символов; пустой список передаётся провайдеру как общий рынок. Root подключает рыночный адаптер на границе `createDigestFunctions(newsProvider)`; default provider работает только с собственными синтетическими данными и отвергает live-режим.
- `sendAuthenticationEmail({userId,url,tokenId,type:'verify_email'|'reset_password'})` — для callback Better Auth, который подключает root. URL строго принадлежит origin приложения. tokenId хэшируется перед записью в event key; сырые токены/URL/адреса в журнале БД не сохраняются. Для verification/reset разрешён ещё неподтверждённый адрес из записи аккаунта; остальные виды требуют `emailVerified=true`.
- Дополнительное поле helper `user:{id,email,emailVerified}` принимается только из доверенного callback BetterAuth. При signup callback выполняется до commit транзакции: новая запись пользователя может ещё не читаться отдельным DB-клиентом. Только verify/reset могут использовать проверенный callback-fallback при отсутствующей DB-записи; id обязан совпадать с userId, email валидируется. Публичный `sendTransactionalEmail` и HTTP-маршруты override не принимают. Существующая DB-запись всегда авторитетна; ошибка DB не заменяется fallback. SMTP внутри auth-транзакции может отправить verification перед последующим rollback: перенос verify/reset в отдельный auth-outbox требует следующего отдельного решения, текущая реализация эту атомарность не обещает.
- `enqueueVerifiedUser(userId)` из `notifications/welcome-outbox` — для `afterEmailVerification`; проверяет подтверждённый адрес и идемпотентно сохраняет intent в Mongo `welcome_outbox` со стабильным `_id`. Callback не вызывает Inngest по сети. Cron `welcome-dispatch` фиксирует snapshot до 100 pending, отправляет `step.sendEvent` со стабильными event IDs и лишь затем отмечает dispatched. Недоступность сети оставляет pending/retriable snapshot. При выключенной почте или stream intent сохраняется до включения SMTP; сразу после регистрации пользователь не подписывается на дайджест.
- `reconcileVerifiedWelcomeUsers()` перед welcome dispatch восстанавливает пропущенный intent для уже подтверждённых пользователей после сбоя verification hook. Mongo `$lookup` использует уникальный индекс `welcome_outbox.userId`; лимит 100 применяется после фильтра отсутствующих intent, поэтому первые 100 давно обработанных аккаунтов не вытесняют новые. Reconcile выполняется при включении SMTP/почты и не отправляет email самостоятельно.
- `/api/inngest` предоставляет GET/POST/PUT SDK. В production требуется cloud event key/signing key, `INNGEST_DEV=1` запрещён, SDK проверяет подпись. `stock/digest.requested{userId,localDate}` обрабатывается отдельно на пользователя; `stock/user.verified{userId}` — одно welcome-письмо. Root подключает эмиттер подтверждения аккаунта. Cron раз в 5 минут и пользовательская функция проверяют `DIGEST_SCHEDULE_ENABLED`.
- `POST /api/email/digest/preview`: локальный ручной прогон только собственной сессии, same-origin, без выбора чужого userId; в production закрыт. Требуется подтверждённый адрес и согласие на дайджест. Результат preview не равен доставке в ящик. `previewOwnDigest(userId, newsProvider?)` допускает тот же provider, который root подключает к расписанию.
- `/api/email/unsubscribe?token=...`: GET показывает только подтверждение и не меняет данные. POST принимает подписанный bearer в Authorization или token из формы подтверждения, отключает только связанный digest. Сессия не нужна; ответ не раскрывает существование адреса. Токен scoped HMAC, срок 90 дней, секрет — `BETTER_AUTH_SECRET`; ротация секрета отменяет старые ссылки. Токен в query используется только на GET, ответы no-store/no-referrer, сторонних ресурсов нет.

Новых env-переменных не добавлено: используется действующая схема config.ts. По умолчанию EMAIL_ENABLED=false, EMAIL_TRANSPORT=stream, DIGEST_SCHEDULE_ENABLED=false, MARKET_DATA_MODE/AI_MODE=fixture. Переключение на SMTP и явное включение отправки требуется отдельно. В production реальная fixture-рассылка и localhost SMTP отклоняются.

## Долговечность и восстановление

Коллекция `notification_deliveries` имеет уникальный `eventKey`; ключи настоящей доставки и preview разделены. Состояния: `pending -> sending -> sent`, либо `skipped`/`uncertain`. Atomic findOneAndUpdate разрешает отправку одному конкурентному исполнителю. Preview формирует MIME через stream, сохраняет skipped/preview и не обновляет `lastSentAt`. Настоящий sent означает принятие SMTP-провайдером; попадание в inbox не подтверждает.

SMTP не предоставляет транзакцию вместе с MongoDB. Разрыв соединения или сбой записи после принятия письма оставляет `uncertain`/`sending`; автоматическая повторная отправка из этих состояний запрещена. `markAbandonedDeliveriesUncertain(before)` переводит только старые sending в uncertain, не делает их pending. Использовать порог значительно больше максимального времени SMTP (20 с) и не запускать восстановление поверх активной отправки.

Известный сбой до вызова SMTP (например, временная недоступность чтения recipient/consent после claim) возвращает запись в pending и выбрасывает безопасную retriable-ошибку. Повтор заново проверяет адрес/согласие и отправляет один раз. Если MongoDB не позволяет сбросить claim, sending сохраняется для ручного восстановления; состояние не сбрасывается без подтверждения отсутствия SMTP side effect.

Для uncertain сначала проверить журнал провайдера по Message-ID и событию, не печатая адрес/контент в общие логи. Если приём подтверждён — оператор согласует фиксацию sent; если однозначно не отправлено — явное отдельное решение о новой попытке с аудитом. При неизвестном исходе сохранить uncertain и уведомить оператора. Автоматического механизма «сбросить всё в pending» нет; такой сброс может создать дубли.

Recipient и digest consent перечитываются из БД после claim непосредственно перед side effect. Неподтверждённый или отписанный пользователь не получает письмо. Регистрация не означает согласие. Уникальный ключ `(userId, localDate)` ограничивает дайджест одним выпуском за локальную дату. Пропущенное время весной при DST обрабатывается на первом последующем tick; повторный час осенью не создаёт второй ключ. Расписание догоняет только текущую локальную дату, не отправляет накопленные выпуски за пропущенные дни.

Новости проходят валидацию, дедупликацию и отбор за последние 24 часа, максимум 6. Gemini получает только заголовки/краткие тексты/даты/ID без email, использует JSON Schema; неизвестные articleIds или неверный формат отвергаются. Ссылки берутся исключительно из проверенного входа. Все тексты и href экранируются при серверном HTML-render. Проверка ID не доказывает смысловую точность каждой фразы модели: до реальной рассылки A/B должны провести содержательную приёмку на согласованном наборе новостей.

Длинные допустимые заголовки сохраняются во входе AI, но подпись ссылки обрезается до 200 символов с многоточием, чтобы пределы новостной схемы (headline 500/source 100) не нарушали email-схему и не приводили к бесконечным повторам.

Диспетчер фиксирует snapshot не более 1000 due-событий в одном durable `step.run`, затем отправляет стабильные группы по 100 через `step.sendEvent`. При replay группы не пересчитываются по уже изменившимся `lastSentAt`, что исключает пропуск адресатов из-за сдвига групп. Более крупная аудитория требует проверки очереди, квот и времени диспетчера перед выпуском; далее due-пользователи подбираются последующими cron.

## Проверки и ограничения
