## Контракт реализации

- Личные GET/POST `/api/alerts`, PATCH/DELETE `/api/alerts/:id`; JSON `ApiResult`, текущая серверная сессия, обязательный Origin у мутаций, строгие входные схемы. Чужой ID не предоставляет доступ. DTO исключает владельца, служебные версии и состояние вычисления.
- `createAlertCollectionHandlers(resolveStock)` принимает проверку существования акции `(symbol: string) => Promise<void>`. Функция должна выбросить `NOT_FOUND`/ошибку поставщика при неподдерживаемом инструменте. В изолированной основе POST использует заглушку, возвращающую 503: основной агент заменяет её рыночным адаптером после объединения этапа 3. Поддельное подтверждение существования не используется.
- Максимум 50 правил на пользователя. Коллекция `alert_rule_owners` сериализует счётчик в транзакции вместе с insert/delete, поэтому одновременные запросы не обходят лимит.
- `alert_rules` содержит version и evaluationRevision, предыдущую цену/условие, источник, время котировки и проверки. Любая правка, пауза и возобновление увеличивают version и сбрасывают baseline. Предыдущее время срабатывания сохраняется, чтобы изменение правила не обходило cooldown.
- Только строгие условия `price > threshold` / `price < threshold`. Равенство порогу — вне обоих условий. Первое наблюдение задаёт baseline и не вызывает письмо. Смена источника или промежуток более допустимого возраста котировки также задают новый baseline.
- Котировки с невалидной ценой/датой, другим символом/валютой, из будущего, старше допустимого возраста или с временем не новее обработанного пропускаются. Время источника определяет порядок; время HTTP не заменяет источник. По умолчанию максимальный возраст — `MARKET_STALE_SECONDS` (900).
- Переход, попавший в cooldown, поглощается. После истечения cooldown письмо не появляется само: нужно выйти из условия и пересечь порог снова. Cooldown не является частотой обхода.
- `processRule` обновляет baseline и вставляет `alert_events` в одной MongoDB-транзакции с majority write concern. Ключ события: `ruleId:version:observedAtISO`. Сбой между фиксацией перехода и отправкой не теряет событие. Конкурирующие проверки одной котировки создают одно событие.
- Редактирование, приостановка и удаление отменяют pending-события в той же транзакции. Доставленные записи остаются для диагностики.

## Экспорты для основного агента

`src/server/alerts/repository.ts`:

```ts
createRule(userId, input, resolveStock)
listRules(userId)
updateRule(userId, id, input)
deleteRule(userId, id)
listActiveRules(limit = 200, afterId?)
processRule(id, quote, now?, { expectedVersion?, maxAgeSeconds? }?)
listPendingEvents(limit = 100)
isEventDeliverable(event)
markEventDelivered(eventKey, now?)
```

Воркер должен обходить все страницы `listActiveRules`, передавая `afterId` последней записи и `expectedVersion` полученного snapshot в `processRule`. Это отбрасывает результаты запроса котировки, если во время запроса пользователь изменил правило. Без expectedVersion сравнивается текущая версия внутри транзакции, а не snapshot внешнего обхода.

`AlertEvent`: `_id` (ключ идемпотентности), ruleId/ruleVersion/userId/symbol/type/threshold/price/currency/source, `observedAt` и `checkedAt` (`Date`), status pending/delivered/cancelled, deliveredAt. Перед отправкой повторно проверить `isEventDeliverable`; использовать `_id` в отдельном журнале/адаптере идемпотентной доставки. После подтверждённой доставки вызвать `markEventDelivered`. SMTP и БД не образуют общей транзакции: абсолютная гарантия одного письма требует идемпотентного почтового провайдера или явного режима неоднозначной доставки. Этот модуль не отправляет письма и не обещает такую гарантию.

`src/server/alerts/evaluate.ts` экспортирует чистый `evaluateQuote` для unit-тестов.

## Проверки и ограничения

Unit-тесты проверяют строгий порог, baseline, cooldown, старую/будущую/повторную котировку и смену источника. Интеграционные тесты на реальной MongoDB 8.0.16 replica set проверяют изоляцию/CSRF/валидацию, лимит при конкурентных create, одно событие при 15 конкурентных проверках, повтор доставки, rollback при ошибке insert outbox, паузу/правку/удаление и пагинацию.

Фактические команды: `npm ci` — выполнено; `npm run lint` и `npm run typecheck` — пройдены; `npm test -- tests/alerts/evaluate.test.ts` — 14/14; `npm run test:integration -- tests/integration/alerts.test.ts` — 9/9, включая конкурентную паузу/удаление во время проверки; `npm run build` и `git diff --check` — пройдены. Production build выполнен без ключей и соединения с рабочими сервисами. Аудит зависимостей при `npm ci` сообщил 5 известных предупреждений исходной dev-конфигурации; состав зависимостей данным этапом не менялся.

Производственные квоты, лицензия и задержка D2 остаются открыты. Возраст 900 с и обход 300 с — предположения локальной разработки. Котировка fixture сохраняет источник fixture в событии; перед реальной рассылкой основной агент обязан исключить синтетические данные. Учётные записи, секреты, внешняя почта и расписания здесь не создаются.

Передано основному агенту B для проверки и объединения. A принимает экран правил после подключения окончательных маршрутов.
