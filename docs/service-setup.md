# Сервисы и параметры разработки

Задачи: P0.2, P0.3. Исполнитель: B. Дата проверки источников: 2026-10-14. Статус: локальный контракт подготовлен; внешние учётные записи и production-права не подтверждены. Этот документ описывает конфигурацию, которую предстоит реализовать в следующих этапах, и не утверждает, что сервисы уже установлены или запущены.

## 1. Локальная среда и границы

| Компонент | Режим разработки | Что требуется для реального использования |
| --- | --- | --- |
| Next.js | Node.js на localhost, без выбранного облачного хостинга | Хостинг с поддержкой Node.js, HTTPS, домен, лимиты выполнения, регион и бюджет |
| MongoDB | Community, только loopback, отдельная БД `ai_stock_market_dev` | Для облака — аккаунт и регион Atlas, отдельные пользователи БД, сетевой доступ, восстановление |
| Рыночные данные | Собственные синтетические фикстуры, provider=`fixture` | Аккаунт Finnhub, доступность нужных endpoint/рынков, фактические квоты, права на показ, хранение и производные сводки |
| Фоновые функции | Inngest Dev Server на localhost:8288 | Production-окружение, подписанный HTTPS endpoint, ключи и оценка executions |
| Email | SMTP в локальный Mailpit; stream transport в unit-тестах | Домен отправителя, подтверждённый провайдер, квоты, согласие/отписка, журнал доставки |
| AI | Детерминированный тестовый адаптер по синтетическим новостям, явно помеченный как тест | Проект Gemini, доступная модель и квоты; права на передачу новостей этому сервису |

D1 (рынки/язык) и экраны принадлежат A. B готовит контракты для тикеров акций США как обратимый тестовый набор; расширение рынков требует handoff A. Владелец подтвердил отсутствие внешних сервисных аккаунтов; локальная MongoDB и Mailpit входят в подготовку среды. Аккаунты и платные облачные услуги автоматически не создаются. Рабочий репозиторий: https://github.com/nazek52/ai-stock-market.git.

## 2. Свежесть и бюджет рыночных данных

Следующие значения — проектные ограничения разработки, а не квоты Finnhub:

| Параметр | Значение | Проверяемое поведение |
| --- | --- | --- |
| Кэш котировки | 60 с | Повторный запрос того же символа в пределах TTL использует одну успешную загрузку |
| Таймаут провайдера | 5 с | Зависший запрос возвращает типизированную ошибку и не блокирует остальные данные |
| Бюджет обращений | 30/мин на приложение, максимум 1 одновременно | Запросы страниц, поиска и фоновых задач используют общий бюджет; при исчерпании — ограничение, без горячего retry |
| Проверка правил | 300 с | Один обход группирует правила по уникальному символу |
| Порог устаревания для правил | 900 с по timestamp источника | Устаревшая/отсутствующая котировка не вызывает уведомление, результат проверки записывается |
| Обновление профиля компании | 24 ч в тестовом кэше | Метаданные не запрашиваются при каждом обновлении цены |
| Новости для сводки | Последние 24 ч относительно запуска | Записи без допустимой даты/ссылки исключаются; отсутствие новостей допустимо |

При live-режиме кэширование и сроки хранения дополнительно должны укладываться в договор провайдера. Для разработки TTL тестируется на собственных фикстурах. В многопроцессной среде лимитер должен быть общим: память одного Node.js-процесса не обеспечивает глобальную квоту. До решения об общем хранилище live-запуски разрешены только с одним экземпляром; это ограничение нужно проверить перед P8.4.

Минимальные метаданные ответа: `provider`, `providerTimestamp`, `fetchedAt`, `stale`, `currency`. Время — ISO 8601 UTC. Невалидное/отсутствующее время не заменяется текущим для создания видимости свежести. Для графиков TradingView источник и время относятся к виджету; ими нельзя подтверждать свежесть собственного адаптера.

Интервал 300 с означает, что обычное ожидание следующего цикла составляет до 5 минут плюс возраст данных и время обработки/доставки. Это расчётная характеристика алгоритма; SLA реального уведомления не установлен. Сохранить метрики `scheduledAt`, `startedAt`, `providerTimestamp`, `evaluatedAt`, `providerAcceptedAt`, чтобы на этапе 7 измерить фактическую задержку. Приём SMTP/API означает принятие провайдером, а не попадание в почтовый ящик.

Официальные [условия Finnhub](https://finnhub.io/terms-of-service) задают дополнительный предел 30 запросов в секунду поверх тарифной квоты. Число запросов в минуту, доступ к endpoint, биржи, задержка и разрешение на распространение именно для аккаунта проекта не проверены. Страницы [тарифов](https://finnhub.io/pricing) и [API](https://finnhub.io/docs/api/rate-limit) динамические; значение «60 запросов/мин» не принимается за подтверждённую квоту аккаунта. Письменное разрешение Finnhub необходимо для передачи данных и производных результатов третьим лицам; персональный план не подтверждает права бизнес-продукта.

## 3. MongoDB

Локально использовать MongoDB Community и отдельную БД для интеграционных тестов. Пример несекретного адреса: `mongodb://127.0.0.1:27017/ai_stock_market_dev`. Установка выполняется отдельно по [официальной инструкции Windows](https://www.mongodb.com/docs/manual/administration/install-community-windows/). Этот адрес не является production-конфигурацией. Не публиковать порт БД в сеть; реальные персональные данные не использовать в тестовых фикстурах.

Atlas Free рассматривается для небольшого тестового стенда. По [официальным ограничениям](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/) доступны 0,5 ГБ, до 500 соединений и 100 операций/с; штатные резервные копии отсутствуют. Поэтому Free не выбран автоматически для production. Перед выпуском нужны проверенное восстановление, лимит connection pool, регион и план хранения журналов. Отдельные базы и секреты для dev/test/production обязательны.

## 4. Inngest и расписание

На этапе 6 локальные функции подключаются к `/api/inngest`, Dev Server — к `http://localhost:8288`. Приложение запускается с `INNGEST_DEV=1`; [официальная инструкция](https://www.inngest.com/docs/local-development) описывает локальный запуск и проверку функций. Production signing key не требуется Dev Server и не должен переноситься в тестовую среду. Для cloud [ключ подписи](https://www.inngest.com/docs/platform/signing-keys) защищает вызов endpoint.

Расписание и реальная отправка изначально выключены флагами. План: один UTC-диспетчер раз в 5 минут выбирает пользователей, для которых наступило локальное время отправки. Значение фикстуры — 09:00 UTC; оно не записывается реальным пользователям без выбора. Ключ выпуска `(userId, localDate)` обеспечивает один выпуск за локальную дату, в том числе при смене DST и повторе события. Ключи/согласие перечитываются непосредственно перед отправкой. Поведение переходов часовых поясов покрывается тестами P6.5.

По [документации расписаний](https://www.inngest.com/docs/guides/scheduled-functions) cron без timezone использует UTC. [Inngest Free](https://www.inngest.com/pricing) публикует 50 000 executions в месяц и 5 одновременных steps; executions включают вызовы функций и шаги. Для двух диспетчеров каждые 5 минут за 30 дней получается 17 280 вызовов до учёта шагов/пользователей/повторов. Квоту считать по фактической структуре функций перед включением cloud, а не по числу писем. Платный план не выбран.

## 5. Почта и AI

Локальная ручная проверка выполняется через SMTP в Mailpit на `127.0.0.1:1025`, просмотр — `http://127.0.0.1:8025`. По [документации Mailpit](https://mailpit.axllent.org/docs/configuration/) это инструмент перехвата тестовой почты; порты контейнера/процесса привязываются только к loopback, SMTP relay/forwarding не включается. Письма остаются в локальном тестовом ящике. Параметры установки и запуска нужно реализовать и проверить в P1.4; документ сам не запускает процесс.

Для unit-тестов подходит [Nodemailer stream transport](https://nodemailer.com/transports/stream): генерируется MIME-письмо без доставки. Письма с синтетическими адресами `example.com` можно проверять в памяти; содержимое и реальные адреса не выводить в обычный журнал. Реальные отправки выполняются только через отдельный адаптер после включения режима доставки. Настройки SMTP не требуются для stream-режима.

Production-кандидат — Resend или выбранный владельцем SMTP-провайдер с журналом результатов. [Resend требует домен и API key](https://resend.com/docs/introduction); [публичные лимиты Free](https://resend.com/docs/knowledge-base/account-quotas-and-limits) — 100 транзакционных писем в сутки UTC и 3 000/месяц. Это кандидат для проверки, не выбор аккаунта или платного тарифа. Пример расчёта: 20 пользователей × 1 дайджест × 30 дней = 600 писем; приветствия, восстановление пароля, уведомления, повторы и входящие письма требуют отдельного резерва. Целевая аудитория и бюджет production пока не согласованы.

Gemini вызывается только на сервере, без email и других данных аккаунта в prompt. В модель передаются разрешённые заголовки/краткие тексты, даты и ссылки. [Квоты Gemini](https://ai.google.dev/gemini-api/docs/rate-limits) зависят от модели и проекта и проверяются в AI Studio. До предоставления проекта модель и числовая квота не утверждены; платный billing не подключается автоматически. Сбой/недоступность AI не должен превращать тестовую сводку в якобы реальный ответ модели.

## 6. Контракт переменных окружения

Предлагаемые имена для P1.3/P1.4; окончательные значения и схема синхронизируются с `.env.example`. Ниже нет секретов и утверждения о готовой реализации.

| Группа | Переменные | Область и смысл |
| --- | --- | --- |
| Приложение | `APP_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET` | URL dev/prod отдельно; secret только серверный, обязателен для реальной авторизации |
| БД | `MONGODB_URI`, `MONGODB_DB` | Серверные, по одному набору на окружение |
| Рынок | `MARKET_DATA_MODE`, `FINNHUB_API_KEY`, `FINNHUB_REQUESTS_PER_MINUTE`, `MARKET_CACHE_TTL_SECONDS`, `MARKET_DATA_MAX_AGE_SECONDS` | fixture/finnhub выбирается явно; ключ обязателен лишь для live; значения 30/60/900 — проектные dev-ограничения |
| Задания | `INNGEST_DEV`, `INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`, `SCHEDULES_ENABLED`, `ALERT_POLL_INTERVAL_SECONDS` | Dev и cloud разделены; расписание выключено; интервал 300 |
| Email | `EMAIL_TRANSPORT`, `EMAIL_DELIVERY_ENABLED`, `EMAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `RESEND_API_KEY` | Локально smtp/127.0.0.1/1025 только в Mailpit; stream для unit-тестов; внешние smtp/resend требуют подтверждённой конфигурации |
| AI | `AI_MODE`, `GEMINI_API_KEY`, `GEMINI_MODEL` | fixture/gemini выбирается явно; режим/модель соответствуют фактическому ответу |

Приватные ключи не получают префикс `NEXT_PUBLIC_`. Production-режим с фикстурами, Mailpit/stream-почтой или локальными ключами должен явно останавливаться на проверке конфигурации либо помечаться как демонстрационный стенд без реальной отправки. Флаг `EMAIL_DELIVERY_ENABLED` относится к внешней доставке: локальное формирование/перехват письма может быть разрешено отдельно и не подтверждает реальную доставку.

## 7. Решения перед production

| Решение | Ответственный | Что предоставить | Что блокируется |
| --- | --- | --- | --- |
| Рынки, UX и тестовые сценарии D1/P0.4/P0.5 | A с владельцем | Подтверждённые рынки, язык, экраны и приёмка | Завершение этапа 0 и интеграция UI |
| Finnhub | Владелец аккаунта + B | Права на публичный показ/рассылку/AI, endpoint, задержка, квота, срок хранения | Публичные live-данные и реальные ценовые уведомления |
| Hosting/Atlas | Владелец проекта + B | Владельцы аккаунтов, регион, бюджет, резервное копирование, доступы через секреты | Развёртывание и подтверждение P8.4 |
| Почта | Владелец домена + B; A проверяет письма | Проверенный домен, сервис, лимиты, тестовый получатель вне Git, согласие/отписка | Реальная отправка дайджеста/уведомлений |
| Gemini | Владелец проекта + B | Проект, разрешённая модель, квоты и правила передачи контента | Генерация сводки внешней моделью |
| Масштаб | A/B с владельцем | Ожидаемые пользователи, символы, правила и ежедневные отправки | Подтверждение бюджета и SLA |

Эти решения не мешают локальному каркасу, типам, авторизации на локальной БД и проверкам бизнес-логики на синтетических данных. При передаче A сообщить точную частоту и источник вместо слова «мгновенно». P0.2/P0.3 остаются частичными до закрытия зависимостей соответствующей среды.
