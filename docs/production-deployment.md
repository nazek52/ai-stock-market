# Подготовка production: участник B, P8.2/P8.4

Публичный выпуск ещё не выполнен. Этот документ описывает подготовленный код и действия после появления реальных аккаунтов, домена и секретов. Прохождение preflight, сборки или readiness само по себе не подтверждает права на данные, доступность поставщиков, доставку почты и полный пользовательский сценарий A.

## Конфигурация и проверка

Секреты вводятся на хостинге через его secret manager либо в локальный игнорируемый `.env.production.local`. Не передавать секреты в Docker build args и не добавлять env-файлы в Git или Docker context. Node.js 24 запускает общий типизированный валидатор напрямую, без компиляции и стороннего dotenv:

```sh
node --env-file-if-exists=.env.production.local scripts/validate-production.mjs
```

При использовании secret manager без файла достаточно `node scripts/validate-production.mjs`. `NODE_ENV=production` должен находиться в предоставленном окружении. Код завершения: 0 — синтаксис и сочетания настроек допустимы, 1 — ошибка. Вывод содержит только имена полей и фиксированные сообщения, без значений ключей, адресов получателей, паролей и URI. Отсутствие необязательного env-файла не создаёт его и не подставляет production-секреты.

| Группа | Требование |
| --- | --- |
| Всегда | `NODE_ENV=production`, публичный HTTPS origin `BETTER_AUTH_URL`, случайный `BETTER_AUTH_SECRET` от 32 символов, `MONGODB_URI` для replica set; `INNGEST_DEV` отсутствует или `0` |
| MongoDB | Для `mongodb://` указать `replicaSet`; SRV допустим, фактический replica set проверяет readiness. Транзакции обязательны для watchlist/alerts |
| Live market | `MARKET_DATA_MODE=finnhub` требует `FINNHUB_API_KEY`; общий бюджет 1–30 запросов/мин |
| Email | Для production-регистрации обязательно `EMAIL_ENABLED=true`: подтверждение email требует `EMAIL_TRANSPORT=smtp`, внешний `SMTP_HOST`, корректные порт/пару credentials и sender; локальный Mailpit и тестовые домены отвергаются |
| События | Включённая почта или расписания требуют `INNGEST_EVENT_KEY` и `INNGEST_SIGNING_KEY`; включённая почта использует welcome outbox |
| Digest | `DIGEST_SCHEDULE_ENABLED=true` требует включённую почту, live market, `AI_MODE=gemini`, `GEMINI_API_KEY`, `GEMINI_MODEL` |
| Alerts | `ALERT_SCHEDULE_ENABLED=true` требует включённую почту и live market; Gemini не требуется |

Выключенные расписания не требуют Gemini/Finnhub, если live market отдельно не включён. Подтверждение email и welcome остаются настроены: без канала подтверждения production-регистрация создала бы недоступные аккаунты, поэтому preflight блокирует такую конфигурацию. Production с явно синтетическим рынком допустим как демонстрационная среда при выключенных расписаниях; это не выпуск live продукта. Welcome/verification письма не требуют Gemini или биржевых ключей. Для внешних SMTP-сокетов без implicit TLS транспорт требует STARTTLS; возможность подключения и подтверждённый sender проверяются у выбранного сервиса отдельно.

Флагов подтверждения лицензии в текущем окружении нет. `EMAIL_ENABLED` и режимы источников обозначают техническую конфигурацию, а не юридическое разрешение. До реальных сводок и уведомлений закрыть D2: права на публикацию/производные данные, покрытие бирж, тариф/квоты, допустимое хранение, ожидаемую задержку. Зафиксировать согласование в `docs/product-decisions.md`; preflight не создаёт и не имитирует это согласование.

## Контейнер

`Dockerfile` использует официальный `node:24-bookworm-slim` в трёх стадиях: зависимости, build, runtime. Root должен включить `output: "standalone"` в `next.config.ts` до финальной проверки контейнера. Runtime копирует traced standalone, static/public и два файла preflight, запускается пользователем `node`. Секреты нужны только при запуске. CMD сначала выполняет preflight, затем `exec node server.js`; неверная конфигурация завершает контейнер до запуска приложения. Базовый tag ограничен Node 24; перед повторяемым production-релизом закрепить проверенный digest образа в процедуре сборки.

```sh
docker build -t ai-stock-market:release .
docker run --rm --name ai-stock-market --env-file .env.production.local -p 127.0.0.1:3000:3000 ai-stock-market:release
```

`.dockerignore` исключает `.env*` на всех уровнях, локальные credentials-файлы основных форматов, `.npmrc`, `.git`, зависимости и результаты сборки. Не добавлять секреты в исходники: ignore не распознаёт произвольно названный файл с секретным содержимым. Reverse proxy завершает TLS, сохраняет корректный внешний host/protocol, origin совпадает с `BETTER_AUTH_URL`; порт Node не публикуется непосредственно в Интернет. Для веб-сервиса и background workflow нужны одинаковые секреты и одна БД/общий бюджет API.

На 2026-10-14 Docker Engine стал доступен, но этот независимый worktree основан на этапе 6 и не использует ещё окончательные сборки этапов 7/8. Контейнер здесь не собирался по указанию основного агента. Финальную Linux-сборку и smoke необходимо выполнить один раз в объединённой ветке после standalone-настройки: запуск nonroot, отказ при неверном env, `/api/health`, `/api/readiness`, реальная replica set и базовый authenticated API. Не объявлять контейнер проверенным до этого прогона.

## Проверки доступности

- `/api/health` — liveness процесса, без доступа к сервисам. При ошибке БД не перезапускать рабочий процесс бесконечно только из-за readiness.
- `/api/readiness` — generic JSON `status: ready`/`unavailable`, HTTP 200/503. Проверяет конфигурацию, ping и writable replica set. Не раскрывает host, имя БД/replica set, ключи и тексты исключений. Ответ `no-store`, внутри процесса кэш 5 секунд и объединение одновременных проверок; предел ожидания 4 секунды.
- Readiness не отправляет письма, не расходует market/AI квоты и не проверяет реальные разрешения на записи/транзакции. Это проверяют отдельные контрольные сценарии в staging, затем в согласованном production-аккаунте.

## Запуск, наблюдение и восстановление

Начинать с выключенных `DIGEST_SCHEDULE_ENABLED`, `ALERT_SCHEDULE_ENABLED`. До публичного открытия настроить и проверить SMTP-путь подтверждения адреса (`EMAIL_ENABLED=true`), БД и HTTPS; затем проверить регистрацию/изоляцию/список. После проверки лицензии, согласия и отписки выполнить одну контролируемую отправку тестовому владельцу, подтвердить идентификатор delivery в журнале и только затем включать расписания. Настройки пользователя не включают согласие на digest по умолчанию.

Наблюдать долю HTTP 5xx/429, readiness, возраст последних котировок, доступность Inngest, количество `notification_deliveries` по status/reason и pending age в outbox. Оповещать оператора о росте `uncertain`, orphan `sending`, давнем pending и отсутствии успешных выпусков у подписанных получателей; не помещать email, ссылки с bearer token, raw provider errors или URI в мониторинговые события.

Остановка новых обходов без отключения регистрации: оба schedule-флага false; обновить окружение, перезапустить процессы, проверить disabled/skip. Аварийное отключение всей отправки: `EMAIL_ENABLED=false` и остановка почтовых workers; в production это также переводит readiness в 503 и блокирует новый запуск контейнера, поскольку регистрация требует подтверждения адреса. Использовать режим обслуживания до восстановления SMTP. Уже принятую SMTP-сервером доставку отозвать невозможно. `uncertain` не переводить автоматически в pending: сначала сверить подтверждение у провайдера. Восстановление БД выполняется из согласованной резервной копии вместе с delivery/outbox состояниями, иначе нарушается защита от дублей. Перезапуск не удаляет журналы.

Ротация: изменить один provider key на целевой стороне и в secret manager, перезапустить соответствующие процессы, выполнить контрольную проверку, затем отозвать старый ключ. `BETTER_AUTH_SECRET` также подписывает unsubscribe-токены: его смена может завершить сессии и аннулирует старые ссылки отписки; подготовить пользователям доступ к настройкам и согласовать переход. Для отката кода сохранять совместимость схем и delivery keys; не откатывать журнал отправок отдельно от приложения.
