# Контракты данных для участника A

P1.3, участник B. Источник типов и схем: `src/contracts/index.ts` (без серверных импортов, безопасен в браузере). Документ описывает согласуемую границу будущих API; наличие типа не означает готовность маршрута. Фактические реализации отмечаются в handoff этапа.

## Общие правила

- Ответ JSON: `{ ok: true, data: T }` или `{ ok: false, error: { code, message, ... } }`. Ошибки различаются по `error.code`; не анализировать текст `message` программно.
- HTTP: `INVALID_INPUT` 400, `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `RATE_LIMITED` 429, `UPSTREAM_UNAVAILABLE` 502, `SERVICE_UNAVAILABLE` 503, `INTERNAL_ERROR` 500. При 429 возможен `retryAfterSeconds`. Поля валидации: `fields?: Record<string, string[]>`.
- Личные ресурсы принадлежат текущей серверной сессии. Клиент не передаёт `userId`: строгие схемы отвергают неизвестные поля. Идентификаторы ресурса в URL не дают права доступа; сервер дополнительно фильтрует по владельцу.
- Мутации вызываются с текущего origin; сервер проверяет origin и сессию. Нельзя передавать секреты Finnhub, Gemini, БД или SMTP в браузер. Ответы не содержат документ MongoDB, внутренние ошибки или cookie сессии.
- Даты — строки ISO 8601 с часовым поясом; отсутствующие показатели — `null`. Цены — конечные числа в валюте инструмента, не строка с символом `$`. UI форматирует их самостоятельно.
- У котировки `source: "finnhub" | "fixture"`; синтетические данные требуют видимой отметки `fixture` и не представляются как котировки Finnhub.

## Ограничения и начальные предположения

Для проектирования принимается обратимое предположение D1: акции США, USD; сервер всё равно обязан подтвердить существование инструмента и его принадлежность рынку по ответу поставщика. Регулярное выражение проверяет только форму тикера (например, `AAPL`, `BRK.B`, `BRK-B`), а не существование. Строки обрезаются по краям и приводятся к верхнему регистру; разные классы акций не объединяются автоматически.

Профиль: имя 1–100 символов; страна — заглавный двухбуквенный код; цель `capital_preservation | income | growth`, риск `conservative | moderate | aggressive`, отрасль — значение `sectorSchema` либо `null`. Сервер не обязан заполнять анкету при регистрации: отсутствующие значения DTO представлены `null`.

Для D3 принимается локальное время `HH:mm` и поддерживаемый IANA timezone (`Asia/Qyzylorda`, `America/New_York`, `UTC`). Хранить отдельно от UTC-момента; переходы DST и защита от повторной отправки реализуются в этапе 6. `enabled: true` означает согласие на ежедневный дайджест, а не согласие на любые письма. При регистрации согласие по умолчанию отсутствует.

Правила первой версии: только `price_above | price_below`, положительный конечный порог до 1 000 000 USD, cooldown целыми минутами 5–10 080, по умолчанию 60. Это границы ввода, не обещание частоты проверок. Интервал обработки и лицензия D2 остаются открытыми; `volume_above` недоступен до решения P7.5. `observedAt` — время самой котировки, `fetchedAt` — время получения приложением; устаревший timestamp не заменять текущим временем.

Клиентские проверки улучшают форму; те же схемы обязательно вызываются на сервере. Требования к отправке почты, проверке существования тикера, квотам, уникальным индексам и авторизации выполняются сервером в следующих этапах.

## Реализованные маршруты B

Этап 6: Better Auth поддерживает `POST /api/auth/send-verification-email`, `GET /api/auth/verify-email`, `POST /api/auth/request-password-reset` и `POST /api/auth/reset-password` в нативном формате Better Auth. В production email должен быть подтверждён; в локальном режиме войти можно сразу. Verification/reset токены действуют час; сброс отозвает старые сессии. Возврат после письма задаётся callbackURL/redirectTo текущего origin. Страницы подтверждения/нового пароля — зона A.

`POST /api/email/digest/preview` доступен только вне production и только для своей сессии; same-origin, не более 3/5 мин. Возвращает результат preview, требует подтверждённый email и включённое предпочтение дайджеста. Preview не доставляет письмо. `GET /api/email/unsubscribe?token=…` показывает подтверждение, `POST` с token из формы либо Bearer отключает дайджест без входа; GET не меняет подписку. Подписанный token является секретом, не отправлять его в аналитику или общий лог.

Этап 7: CRUD `/api/alerts` и `/api/alerts/:id` реализован с проверкой владельца, same-origin и лимитом мутаций 60/мин на пользователя. Максимум 50 правил; DTO не раскрывает владельца/внутреннее состояние. Первое наблюдение нового/изменённого/возобновлённого правила задаёт baseline и не отправляет письмо; нужен новый переход через строгий порог. Равенство порогу не является срабатыванием. Cooldown подавляет переход, новый переход после него необходим для следующего письма. `volume_above` отклоняется схемой.

Этап 5: все три операции watchlist реализованы. Максимум 50 акций на пользователя, POST 201 при создании и 200 при повторе; лимит — 409 CONFLICT. DELETE возвращает deleted:false для отсутствующей собственной записи, включая случай наличия такого символа только у другого пользователя.

Этап 2: `/api/auth/*` с нативным JSON Better Auth, профиль и предпочтения дайджеста. Этап 4: поиск, quote, company, news. Рыночные операции требуют сессию и ограничены 60 HTTP-запросами за минуту на пользователя; общий сетевой бюджет Finnhub - до 30/мин. Ответы рынка содержат `X-Market-Data-Mode: fixture | finnhub`; UI обязан маркировать синтетический режим и не выдавать его за реальные данные. Настоящий Finnhub пока не проверен ключами аккаунта.
