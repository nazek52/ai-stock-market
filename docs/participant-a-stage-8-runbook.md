# P8.5 — запуск и восстановление AI Stock Market

Черновик участника A, 2026-10-14. Команды ниже проверяются в отдельной среде перед выпуском; выбранный production-хостинг, домен, MongoDB, SMTP и доступы пока не зафиксированы. Ответственный за инфраструктуру и production-конфигурацию — B (P8.4). Секреты и данные пользователей не помещать в Git, общие логи и тикеты.

## 1. Инвентаризация перед запуском

1. Зафиксировать адрес приложения с HTTPS, владельца/регион/резервное копирование MongoDB replica set, исходящий SMTP с подтверждённым доменом, Inngest Cloud, права/квоты Finnhub и Gemini. Проверить разрешение на показ и рассылку рыночных данных и передачу новостей в AI. Для каждого секрета назначить владельца и способ отката.
2. В секретном хранилище окружения задать `BETTER_AUTH_URL` (точный HTTPS origin), случайный `BETTER_AUTH_SECRET` (минимум 32 символа), `MONGODB_URI`, `MONGODB_DATABASE`, `INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`, `FINNHUB_API_KEY`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `EMAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`. Установить `MARKET_DATA_MODE=finnhub`, `AI_MODE=gemini`, `EMAIL_TRANSPORT=smtp`, `INNGEST_DEV=0`. Числовые переменные рынка и расписания согласовать с фактическими квотами. Не копировать локальный `.env.local` в production.
3. Начинать с `EMAIL_ENABLED=false`, `DIGEST_SCHEDULE_ENABLED=false`, `ALERT_SCHEDULE_ENABLED=false`. Подтверждение email обязательно в production; до включения SMTP/email новые пользователи не смогут завершить регистрацию, а восстановление доступа не доставит ссылку. Планировать открытие регистрации вместе с проверкой почты.
4. На том же зафиксированном коммите в отдельной CI/тестовой среде выполнить `npm ci`, `npm audit --omit=dev --audit-level=high`, `npm run check`, `npm run test:integration`. Последняя команда запускает временные MongoDB replica set, требует доступного бинарника MongoDB; её не запускать с production-секретами или на production-хосте. В CI эти шаги есть в `.github/workflows/ci.yml`.
5. Развернуть зафиксированный артефакт способом выбранного хостинга, выполнить `npm run start` для Node.js приложения. Настроить Inngest на `/api/inngest`; проверять ключи подписи/событий без вывода значений. Отдельный production deployment сценарий и подпись артефакта в репозитории пока отсутствуют: B должен заполнить конкретные команды хостинга и шаги отката.

## 2. Проверка после запуска

- `GET https://<домен>/api/health` должен вернуть `{"status":"ok"}`. Это **только liveness**; маршрут не проверяет MongoDB, SMTP, Finnhub или Inngest. Проверить их отдельными синтетическими действиями и журналами провайдеров.
- Открыть `/`, `/search`, `/login`, `/settings`; проверить сертификат, ошибки страницы, консоль браузера и состояние клавиатурной навигации. Для защищённых маршрутов выполнить вход тестовым подтверждённым аккаунтом. Проверить сохранение watchlist и настроек после обновления страницы.
- Проверить регистрацию и письмо подтверждения на тестовый адрес, затем запрос сброса пароля. Состояние `sent` в `notification_deliveries` означает приём SMTP, не доставку во входящие. Подтвердить доставку по журналу почтового провайдера и ящику.
- Включать `EMAIL_ENABLED=true` после проверки транспорта/домена. Затем отдельно включать `DIGEST_SCHEDULE_ENABLED=true` и, после сквозной приёмки alert worker, `ALERT_SCHEDULE_ENABLED=true`. Перезапустить/переопубликовать все экземпляры и worker-процессы с новым окружением. Проверить один выпуск на согласившемся тестовом аккаунте, отсутствие выпуска после отписки и отсутствие дубля при повторе события.
- P8.1 принимается только по фактическому сквозному сценарию на рабочем адресе: регистрация → подтверждение → поиск → watchlist → согласие на сводку → письмо → правило → переход порога → одно письмо → отписка. Dev preview и fixture не подтверждают production-доставку, работу живых квот или лицензионные права.

## 3. Остановка рассылок при инциденте

1. При ошибке содержания/адресатов сначала установить `DIGEST_SCHEDULE_ENABLED=false` и `ALERT_SCHEDULE_ENABLED=false` во всех экземплярах и перезапустить/redeploy. Digest dispatcher/user handler и alert worker проверяют флаги при выполнении; отдельно проверить уже запущенные задания и pending-события. Уже отправленные SMTP-письма вернуть нельзя; Inngest-выполнения и очередь проверить отдельно.
2. Для немедленной общей остановки исходящей доставки также поставить `EMAIL_ENABLED=false` и перезапустить все экземпляры. Это затронет welcome, подтверждение адреса и восстановление пароля. `EMAIL_TRANSPORT=stream` не является production-переключателем доставки; оставлять `smtp`, но отключить флаг. Зафиксировать время остановки и номер релиза.
3. Проверить Inngest Dashboard, SMTP-провайдера и записи `notification_deliveries` по типу/статусу; не выводить адреса, тело писем или токены в общий лог. На время расследования не включать автоматический повтор `uncertain`/`sending`.
4. После исправления содержания, согласия, данных и квот сначала пройти тестовый выпуск/уведомление, затем включать по одному флагу и наблюдать отдельный цикл. Дайджест догоняет только текущую локальную дату; пропущенные дни автоматически не рассылаются.

## 4. Восстановление БД и доставка с неопределённым исходом

- Для production использовать согласованные B/P8.4 snapshot/backup и retention MongoDB, до запуска провести восстановление **в отдельную изолированную БД**. Зафиксировать RPO/RTO и проверку целостности `user`, `session`, `watchlist_items`, `digest_preferences`, `notification_deliveries`, `welcome_outbox` и коллекций правил B7. MongoDB Atlas Free без штатных backups не подходит для обещания восстановимого production. Не перезаписывать работающую БД без отдельного решения об откате.
- Для локальной разработки `npm run services:up` запускает Docker MongoDB replica set и Mailpit; `npm run services:down` останавливает их, сохраняя Docker volume. Без Docker `npm run services:mongo` сохраняет файлы в `.local/mongodb`; останавливать Ctrl+C и ждать чистой остановки. Эти способы не являются production backup. `npm run setup:local` создаёт `.env.local` один раз и не перезаписывает существующий файл.
- После аварии собрать время сбоя, статус Inngest и SMTP, snapshot БД и количество `pending`, `sending`, `uncertain`, `sent`, `skipped` в `notification_deliveries`. `eventKey` уникален; `preview:` и `delivery:` имеют разные пространства. Не сбрасывать все записи в `pending`.
- `sending` старше максимального времени SMTP может быть переведён функцией `markAbandonedDeliveriesUncertain(before)` в `uncertain` только после исключения активных отправок; в коде нет административного CLI для этой операции. B должен подготовить контролируемый операторский способ и аудит. Для `uncertain` сверить `eventKey`/Message-ID с журналом провайдера: подтверждённый приём — согласовать отметку `sent`; подтверждённое отсутствие отправки — отдельное решение о повторе; неизвестный исход — оставить `uncertain` и эскалировать. Вручную не менять статус без протокола решения: SMTP и MongoDB не образуют одну транзакцию.
- После восстановления БД заново проверить согласие, подтверждение email, ссылки отписки, уникальные индексы, одну безопасную тестовую отправку и отсутствие повторов. При рассинхронизации с провайдером не запускать массовое восстановление очереди вслепую.

## 5. Ротация ключей

| Ключ | Порядок и влияние |
| --- | --- |
| `BETTER_AUTH_SECRET` | Сгенерировать новый в secret store, согласованно обновить все экземпляры, перезапустить, проверить вход/выход и восстановление. Смена секрета инвалидирует старые подписанные ссылки отписки (срок до 90 дней) и может нарушить существующие сессии/токены. Перед плановой сменой подготовить повторную выдачу ссылок и поддержку пользователей. При компрометации приоритет — немедленная замена и инвалидирование. |
| `INNGEST_SIGNING_KEY`, `INNGEST_EVENT_KEY` | Сверить последовательность смены с Inngest Cloud и задействовать поддерживаемый им период перекрытия, если есть; обновить секреты всех экземпляров, проверить подписанный вызов `/api/inngest` и отправку события. Не отключать проверку подписи. |
| SMTP credentials | Создать новый ключ у провайдера, обновить секрет, выполнить тестовое письмо и проверить журнал приёма, затем отозвать старый. Проверить `EMAIL_FROM` и доменную аутентификацию. |
| `FINNHUB_API_KEY`, `GEMINI_API_KEY` | Обновить в secret store, проверить один допустимый запрос каждого сервиса и квоты, затем отозвать прежний ключ. Не раскрывать содержимое заголовков/секретов в логах. |
| MongoDB credentials | Создать нового пользователя с минимальными правами и проверенным доступом, обновить URI во всех экземплярах, проверить чтение/запись и replica set, затем отозвать старого. Планировать окно, поскольку соединения могут жить дольше одного запроса. |

Дата, владелец, затронутая среда, тесты и отзыв старого секрета фиксируются в закрытом журнале изменений. Никогда не печатать целые URI с паролями и значения ключей в командах/CI output.

## 6. Откат релиза

1. Остановить расписания флагами из §3 и зафиксировать текущий commit/артефакт, ошибки, время, версию схемы и состояние delivery. Проверить, может ли предыдущий релиз читать текущие документы БД; явных migration/rollback скриптов в репозитории нет.
2. Вернуть предыдущий проверенный артефакт через механизм хостинга, сохранив согласованные секреты и БД. Если нужен откат данных, восстановить snapshot в изолированную среду и оценить потерю новых аккаунтов/согласий/событий; решение о production restore принимает B/владелец данных.
3. Проверить `/api/health`, вход, чтение/запись тестовой записи, подпись Inngest, SMTP, пользовательские страницы и журналы ошибок. Включать расписания после проверки idempotency и сверки неопределённых доставок. Зафиксировать результат и причины инцидента.

## 7. Ограничения этого черновика

Production-хостинг, HTTPS-домен, лицензия Finnhub, почтовый провайдер, Gemini-квота, реальные backups/restore, живой прогон alert worker и мониторинг ещё не подтверждены. `GET /api/health` не является readiness. Точный порядок флагов/секретов и команды deploy/rollback B должен дополнить после выбора платформы, а A — проверить сквозным пользовательским сценарием.
